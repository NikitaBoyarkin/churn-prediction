# EDA Findings — churn-prediction (synthetic subscription churn)

**Дата:** 2026-10-13
**Полный отчёт:** `reports/eda/eda-churn-2026-10-13.md`

## Датасет вкратце

`data/users.csv` (12,000 строк, одна строка = пользователь) + `data/activity.csv`
(455,443 строки, одна строка = один активный user-day). Период: signup 2023-06-01 .. 2024-01-31,
активность 2023-06-01 .. 2024-05-01. Синтетика, seed=42. Качество данных — **хорошее**:
0 пропусков, 0 дублей, 0 сирот FK, все диапазоны валидны; все аномалии структурные
(цензурирование, границы покрытия), а не ошибки сбора.

## Топ проблем качества

### Проблема 1: базовая churn rate 17.4% — смесь двух режимов, не ставка оттока
- **Что:** на тестовом снапшоте 2024-03-15 полная когорта n=5,581 даёт churn 17.4%, но это
  средневзвешенное censored-группы (n=3,889, churn 0.10%) и at-risk группы (n=1,692, churn 57.2%).
  69.7% когорты — near-guaranteed negative: их окно метки не содержит 30 тихих дней.
- **Влияние:** любая метрика churn на полной когорте занижена вдвое и не описывает продукт;
  сравнение каналов на полной когорте даёт ложный эффект (см. проблему 2).
- **Действие:** считать churn только на at-risk срезе; base_rate 17.4% не публиковать как
  churn rate. Правильный фикс — пере-генерация без cap `death_date` на HORIZON.
- **Владелец:** аналитик (метрика) + дата-инженер (генератор).
- **Уже задокументировано в README** (Limitations) — это подтверждение, не новая проблема.

### Проблема 2: «эффект канала» ×2.69 — артефакт цензурирования (Simpson's paradox)
- **Что:** churn по `channel` на полной когорте: paid_search 27.5% vs referral 10.2% (×2.69).
  Внутри at-risk группы разрыв схлопывается до ×1.13 (social 61.7% .. organic 54.7%), и
  paid_search перестаёт быть лидером. At-risk доля по каналу: 48.1% (paid_search) vs 18.3%
  (referral); срок жизни 77 vs 157 дней.
- **Влияние:** наивный вывод «paid_search приносит худших пользователей» — ложный; канал лишь
  прокси срока жизни. Решения по каналам на полной когорте будут ошибочны.
- **Действие:** стратифицировать по `lifetime_days` / at-risk; докладывать каналы только на at-risk срезе.
- **Владелец:** аналитик.

### Проблема 3: right-censoring — 29.2% пользователей обрезаны на горизонте
- **Что:** `death_date` = HORIZON (2024-05-01) у 3,508 из 12,000 (29.2%) — структурный sentinel,
  истинный срок жизни неизвестен.
- **Влияние:** распределение `lifetime_days` (median 101, p95 273) недооценивает правый хвост;
  survival-оценки смещены.
- **Действие:** при работе со сроком жизни — Kaplan-Meier / censored-aware методы; не читать
  `lifetime_days` как полный срок.
- **Владелец:** аналитик.

### Проблема 4: 31 пользователь без единого активного дня
- **Что:** 11,969 из 12,000 `user_id` есть в `activity.csv`; 31 (0.26%) отсутствуют.
- **Влияние:** минимальное (0.26%); при join'ах users → activity дадут NaN-активность.
- **Действие:** задокументировать ожидаемую долю 0.26% как ветвь генератора
  (`generate_data.py:78`); не считать ошибкой.
- **Владелец:** дата-инженер.

## Что в порядке

- Обе таблицы — 0 пропусков, 0 полных дублей, 0 дублей по ключу (`user_id`;
  `(user_id, active_date)`), 0 сирот FK.
- Все диапазоны валидны: `death_date` ≥ `signup_date`; `sessions` ∈ [1,4]; `events` ∈ [1,20];
  даты без будущих и раньше старта системы.
- 0 выбросов по IQR в `lifetime_days` и `sessions`.
- Все 10 data-level утверждений README воспроизведены точно (0 MISMATCH).
- Поведение (sessions/active-day) стабильно всю историю: 2.464–2.529, flat.
- Покрытие по датам непрерывно 2023-06-01 .. 2024-05-01, разрывов нет.
