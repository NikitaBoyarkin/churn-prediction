# EDA — churn-prediction (synthetic subscription churn)

> [!summary]
> Синтетический датасет churn-модели: 12,000 пользователей и 455,443 активных user-day.
> Разбирали, чтобы проверить data-level утверждения README и понять, что несут признаки.
> Данные чистые (0 пропусков, 0 дублей, FK без сирот). Главная находка: **видимый эффект
> канала на churn — артефакт цензурирования и срока жизни**, а честная churn rate
> (57.2%) вдвое выше «базовой» 17.4%, потому что 69.7% когорты физически не могут
> заchurn'ить внутри окна. Все data-level цифры README воспроизведены; model-метрики
> (lift/AUC) — NOT-CHECKABLE.

## Executive Summary

- **Датасет:** `data/users.csv` (12,000 строк) + `data/activity.csv` (455,443 строки),
  синтетика seed=42. Период: signup 2023-06-01 .. 2024-01-31, активность 2023-06-01 .. 2024-05-01.
- **Grain:** `users.csv` — один пользователь; `activity.csv` — один активный user-day (не календарный день: неактивные дни отсутствуют как строки).
- **Целевая метрика:** `churn` (бинарная, вычисляется as-of снапшот). На тестовом снапшоте 2024-03-15: base rate **17.4%**, честная at-risk churn **57.2%**.
- **Производная метрика:** `lifetime_days` — медиана **101 дн**, p95 **273 дн**, skew 0.69 (умеренная).
- **Главный разрыв (полная когорта):** `channel` — `paid_search` 27.5% vs `referral` 10.2% (**×2.69**).
- **Состояние данных:** чисто — 0 пропусков, 0 полных дублей, 0 дублей по ключу, 0 сирот FK, диапазоны валидны.
- **Главный вывод:** «эффект канала» на churn в основном **не эффект канала** — это композиция цензурирования и срока жизни (Simpson's paradox): внутри at-risk группы разрыв схлопывается с ×2.69 до ×1.13.

## Распределения

- **`lifetime_days`** (производная): mean 113.4, median 101, p95 273, max 335, min 5,
  **skew 0.69** (умеренная) → среднее ≈ медиана, докладываем медиану. Распределение
  унимодальное с правым хвостом. **Right-censored**: 29.2% наблюдений обрезаны на HORIZON,
  поэтому истинный хвост срока жизни недооценён.
- **`sessions`** (на active-day): mean 2.501, median 3, диапазон [1,4], skew ≈ 0 —
  почти вырожденное дискретное; **behaviour стабилен**.
- **`events`**: mean 7.50, median 6, skew 0.84, диапазон [1,20] — умеренно скошенный,
  вторичная метрика (производная от sessions).
- **`user_id`**: равномерный 1..12000 (0% выбросов) — ID, не признак.

## Сегменты

Churn rate на тестовом снапшоте (2024-03-15, n = 5,581), полная когорта:

| Разрез | Макс | Мин | Разрыв (max/min) |
|---|---|---|---|
| **channel** | paid_search **27.5%** | referral **10.2%** | **×2.69** |
| device | web 20.4% | android 15.9% | ×1.28 |
| country | KZ 20.3% | BY 15.5% | ×1.31 |
| plan | pro 18.0% | basic 16.6% | ×1.09 |

`channel` — единственный разрыв выше порога `SEGMENT_GAP_WARN = 1.5` (×2.69). Кандидат в главный вывод.
`plan` практически не влияет (×1.09), `device`/`country` слабо (×1.28–1.31).

**Проверка на композицию (Simpson's paradox).** Разрыв по каналу НЕ объясняется составом планов:
доля `free` по каналам 0.59–0.62 (почти идентично). Но он объясняется **цензурированием**:
- at-risk доля по каналу: paid_search **48.1%**, social 40.1%, email 32.4%, organic 25.1%, referral **18.3%**;
- срок жизни по каналу: referral 157 дн, organic 130, email 115, social 101, paid_search **77 дн**;
- внутри at-risk группы churn по каналу: social 61.7%, paid_search 57.1%, email 56.1%, referral 55.3%, organic 54.7% → разрыв **×1.13** (paid_search даже не лидер).

То есть канал — прокси срока жизни: короткоживущие каналы (paid_search) поставляют больше
«at-risk» пользователей в когорту, что и раздувает их churn на полной выборке. Это ровно тот
механизм, который README описывает как «mixture artifact». Рисунок:
`figures/fig2_churn_by_segment.png`, `figures/fig5_channel_paradox.png`.

**Цензурирование как главный стратификатор.** На тестовом снапшоте:

| Группа | n | Churn rate |
|---|---:|---:|
| Censored (`death_date` ≥ label_end) | 3,889 (69.7%) | **0.10%** (4 из 3,889) |
| At-risk (`death_date` < label_end) | 1,692 (30.3%) | **57.2%** (967 из 1,692) |
| Полная когорта (mixture) | 5,581 | 17.4% |

Рисунок: `figures/fig4_censoring_stratification.png`.

## Динамика и аномалии

Колонка времени есть (`active_date`, `signup_date`) — Phase 5 применима. Недельная динамика
активности, 49 недель:

- **Поток (flow):** активные user-day/неделю растут с 182 (июнь 2023) до пика **13,939**
  (неделя 2024-02-04), затем монотонно падают до 3,024 в последней неделе. Падение с февраля —
  реальный отток пользователей (они churn'ят и перестают генерировать активность).
- **Поведение (behaviour):** sessions на active-day **плоский** всю дорогу — min 2.464,
  max 2.529, медиана ≈ 2.50. Вся недельная динамика — **поток**, не поведение.
- **Аномалия последней недели:** 2024-04-29 даёт −58%, но это **не падение** — данные
  обрываются на HORIZON 2024-05-01, неделя неполная (3 дня из 7). Помечено на графике.
- **Аномалия `users` по `signup_date`:** неделя 2024-02-04 = −50% — тоже граница покрытия
  (signup заканчивается 2024-01-31), не инцидент.
- **Day-of-week:** активные user-day почти равномерны по дням недели (64,613–65,661) —
  выходного эффекта нет.

Рисунок: `figures/fig3_activity_trend.png`.

## Findings (E / H / R)

### Finding 1: «Эффект канала» на churn — артефакт цензурирования и срока жизни

**Evidence:**
- Полная когорта: churn по `channel` ×2.69 (paid_search 27.5% vs referral 10.2%, n=5,581).
- Внутри at-risk группы: ×1.13 (social 61.7% .. organic 54.7%) — разрыв почти исчезает.
- At-risk доля по каналу: paid_search 48.1% vs referral 18.3%; срок жизни: 77 vs 157 дней.
- Состав планов по каналам идентичен (free 0.59–0.62) → это не композиция планов.

**Hypothesis:**
- H1: «Канал влияет на churn только через срок жизни: короткоживущие каналы быстрее
  "выгорают" и поставляют больше at-risk пользователей, что раздувает их churn на полной выборке».
- H2 (альтернативная): канал имеет независимый поведенческий эффект, который маскируется
  внутри at-risk группы малым n (54.7–61.7% при n=175–1036). `[❓ требует валидации]`

**Recommendation:**
- Действие: докладывать churn по каналам **только на at-risk срезе** (или стратифицировать по
  сроку жизни), а полную когорту не использовать как KPI канала.
- Рычаг: `churn ↓` (retention)
- Сценарий проверки: стратифицированный анализ / ковариационный контроль по `lifetime_days`;
  для реального продукта — удержание по каналам с контролем tenure.
- Приоритет: **H**

### Finding 2: честная churn rate — 57.2%, а не 17.4%

**Evidence:**
- Полная когорта n=5,581: base_rate 17.4%.
- Censored (n=3,889, 69.7%): churn 0.10% (4 пользователя).
- At-risk (n=1,692, 30.3%): churn 57.2% (967 пользователей).
- 17.4% — средневзвешенное двух режимов (~0.001 и ~0.57), а не ставка оттока.

**Hypothesis:**
- H1: «69.7% когорты — near-guaranteed negative по конструкции генератора (`death_date` capped
  at HORIZON): их окно метки не содержит 30 подряд тихих дней». (Это документированное README ограничение.)
- H2: часть «censored» пользователей реально churn'нула, но метрика этого не видит → 57.2%
  может быть заниженной. `[❓ требует валидации]`

**Recommendation:**
- Действие: любую метрику churn считать на at-risk срезе; base_rate 17.4% не публиковать как
  churn rate продукта.
- Рычаг: `churn ↓`
- Сценарий проверки: пере-генерация данных с реалистичным `death_date` (не capped), повторный замер.
- Приоритет: **H**

### Finding 3: данные чистые — качество не блокирует анализ

**Evidence:**
- 0 пропусков, 0 полных дублей, 0 дублей по `(user_id, active_date)`, 0 сирот FK в обеих таблицах.
- 0 выбросов по IQR в `lifetime_days` и `sessions`.
- Все диапазоны валидны: `death_date` ≥ `signup_date`, `sessions` ∈ [1,4], `events` ∈ [1,20].
- Все 7 data-level утверждений README воспроизведены точно (см. Truth check).

**Hypothesis:**
- H1: «Синтетический генератор детерминирован (seed=42) и самоконсистентен, поэтому raw-таблицы
  не несут ошибок сбора — все аномалии структурные (цензура, границы покрытия)».

**Recommendation:**
- Действие: перейти к анализу/моделированию без фикса данных; зафиксировать grain и
  структурные sentinel'ы в data dictionary.
- Рычаг: `time_to_convert ↓` (аналитика быстрее)
- Сценарий проверки: не требуется — принято по факту прохождения порогов.
- Приоритет: **L**

### Finding 4: поведение стабильно, динамику двигает поток

**Evidence:**
- sessions/active-day плоский: min 2.464, max 2.529 (49 недель).
- Активные user-day: 182 → пик 13,939 → 3,024; падение с февраля 2024 монотонное.
- Последняя неделя −58% — неполная (данные кончаются 2024-05-01).
- Day-of-week равномерен (64,613–65,661).

**Hypothesis:**
- H1: «Падение активности после февраля — реальный накопленный отток, а не деградация
  инструментирования: поведение на активного пользователя не меняется».
- H2: снижение — артефакт генератора (пул активных исчерпывается к горизонту). `[❓ требует валидации]`

**Recommendation:**
- Действие: в отчётности разделять flow и behaviour; не читать последнюю неделю как падение.
- Рычаг: `churn ↓`
- Сценарий проверки: когортный анализ по снапшотам (cohort-analysis).
- Приоритет: **M**

### Finding 5: 31 пользователь без единого активного дня

**Evidence:**
- 11,969 из 12,000 `user_id` присутствуют в `activity.csv`; 31 отсутствуют.
- У всех 31 `death_date` > `signup_date` (не вырожденные), т.е. это не пустые записи.
- Генератор пропускает пользователя, если случайный бросок не дал ни одного активного дня
  (`generate_data.py:78`).

**Hypothesis:**
- H1: «Это редкая ветвь генератора: пользователь с низкой `p_active` и коротким сроком жизни
  может не сгенерировать ни одного активного дня».
- H2: ошибка данных / потерянные строки. `[❓ требует валидации]` — но 0.26% и логика генератора
  указывают на H1.

**Recommendation:**
- Действие: задокументировать как ожидаемую долю 0.26%; не считать ошибкой.
- Рычаг: `time_to_convert ↓`
- Сценарий проверки: проверка доли при пере-генерации с другим seed.
- Приоритет: **L**

## Что не вошло

- **Model-метрики не пересчитаны.** lift@top-decile, ROC-AUC, PR-AUC, Brier, SHAP — требуют
  полного пере-обучения LightGBM + LogReg и доступа к feature-frame (`src/features.py`).
  EDA работала на raw-таблицах + собственной ре-деривации лейбла; модель не запускалась.
- **Feature-frame не реконструирован.** Признаки (`recency_days`, `recent_trend`,
  `active_ratio_30` и т.д.) не пересчитывались и не проверялись на распределения/корреляции.
  Проверено только то, что лейбл и n по снапшотам совпадают с `metrics.json`.
- **Генератор не аудирован на реалистичность.** Данные синтетические; правдоподобие
  CHANNEL_TENURE / PLAN_ACTIVE — допущение генератора, а не измерение.
- **Right-censoring не устранён.** `death_date` capped at HORIZON 2024-05-01 → у 29.2% users
  истинный срок жизни неизвестен; распределение `lifetime_days` недооценивает хвост.
  Survival-анализ (Kaplan-Meier) не проводился — вне рамок EDA.
- **Нет доверительных интервалов.** Все churn-ставки — точечные оценки на одном снапшоте;
  bootstrap/CI не считались (README это тоже отмечает).
- **at-risk маска — oracle.** Использует `death_date`, недоступный в проде; применена только
  для стратификации оценки, в признаки не попадает (`test_feature_columns_are_allowlisted`).
- **Неактивные дни не наблюдаемы.** `activity.csv` содержит только активные user-day; разница
  «неактивен» vs «churn'нул» в конкретный день без `death_date` неразличима.
- **Внешний бизнес-контекст отсутствует** — нет цены, выручки, стоимости удержания;
  рекомендации ограничены метрикой churn, не деньгами.
